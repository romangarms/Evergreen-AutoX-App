# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FastAPI server (`server/app.py`) wrapping the Speedhive/MYLAPS API for Evergreen AutoX race results. An iOS app will be added to this repo later; until then the server is the whole project.

The Android app (`Evergreen AutoX App Android/`, Kotlin + Compose, package `com.romangarms.autoxlive`, permanent) is a read-only port of the iOS app: no accounts, posting or push yet, shown as "coming soon". It installs as a signed APK from `/android` and updates itself through `GET /api/android/release`.

## Running

- `./start.sh` — prompts for a leaderboard admin password if `.env` lacks one, then runs `docker compose up -d --build` if Docker Compose is available (the public server's deploy path) or otherwise creates `.venv`, sources `.env`, and runs the server in the foreground. `./start.sh local` forces the venv path (use this for dev on the Mac, which has Docker installed); `./start.sh set-password` changes the credentials. Running `./.venv/bin/python server/app.py` directly skips `.env`.
- Serves on port 8321, bound to `0.0.0.0` intentionally so an iPhone on the same LAN can reach the Mac during development — do not change it to `127.0.0.1`.
- The public deployment is https://autox.romangarms.com (a reverse proxy terminates TLS and forwards to port 8321). The iOS app's default base URL lives in `AppModel.defaultBaseURL`; `Info.plist` only permits insecure HTTP for local-network addresses, so any non-LAN server must be HTTPS.

## Lint/format

- `./.venv/bin/ruff check .` and `./.venv/bin/ruff format .` (config in `ruff.toml`).
- `./.venv/bin/python -m pytest` runs `tests/`. `conftest.py` sets the admin credentials before importing `app`, and its `client` fixture points `db.DB_PATH` at a temp database per test; `device(name)` returns Bearer headers for a signed-in device. `tests/data/drag_quarter_mile.csv` is a real TrackAddict drag log cut down to its GPS samples with the coordinates replaced.

## Gotchas

- **GGLC publishes result pages with a title and no tables** (e.g. 2026-08-29). `gglc.list_events` drops pages without runs unless the event is today, and `fetch_event` never caches them, so a page filled in later shows up on its own. GGLC rewrites the page in place, so a poll can catch it empty or cut short: an empty page never replaces the saved copy, a page with fewer runs only does once it has stayed short for `SHRINK_GRACE`, a failed HEAD probe leaves the day to be asked again rather than failing the list, and both apps keep the GGLC events already shown for a year whose list fails to load. GGLC also deletes old pages (and has reused one for test data), so every page with results is saved to `gglc_events`; once its day has passed (`final`) the saved copy is served and GGLC is never asked again. Events whose page is gone come from GGLC's result PDFs (`ggautox/<year>results/GGLC_results_MMDDYYYY.pdf`), imported with `python server/gglc_pdf.py YEAR...` as final rows with `source` `pdf`, which replace a saved live page. The PDFs are the live results workbook printed from Excel, so `gglc_pdf.py` rebuilds the sheet's cells from the drawing (grid lines, fills, Excel's down-then-over page order) and feeds them to `_parse_table`. Some were printed without the highlight on the scored run, so a row without one gets the best of its first five runs; a highlight always wins, because GGLC's Indexed column follows it. A sheet's run columns are not one per run (2026-11-08 had ten morning columns, mostly blank, then the afternoon's), so `run` counts a driver's non-blank cells and `column` keeps the cell's position; the apps' compare views line runs up by `column` (`Run.slot`), everything else uses `run`. A car still on course shows `0.000` on the live page; `_parse_run` drops it like a blank cell, and the apps and `notify.py` ignore any GGLC total that is not above zero (`GGLCRun.score`, `_gglc_total`), so saved pages that carry one never rank it first.
- **Live results refresh themselves, and the server absorbs the polling.** `RootView` calls `AppModel.refreshSessionData()` every 10 seconds while the app is active, a results page is showing, and the event is dated today or yesterday (`wantsLiveRefresh`); it shows no spinner, and a failure only marks the results as old. `server/cache.py` holds each Speedhive/GGLC answer for `LIVE_TTL`/`LIST_TTL`, so upstream load does not grow with users; route any new upstream call through `cache.cached`. Only one caller per key asks upstream at a time; while it waits, or after it fails, everyone else gets the last answer (up to `STALE_LIMIT` old), and a failure is remembered for `FAILURE_TTL`. That is what keeps a stalled Speedhive from tying up every server thread, so keep fetches out of any lock, and keep the Speedhive client's short timeout and single retry (`app.py`). Driver and compare screens are addressed by position, which a refresh can change, so `AppModel.show` moves an open screen to its driver's new position and `NavRoute` leaves positions out of its identity to keep that from animating as a navigation.
- **Both apps keep the last answer to every results GET on disk** (`ResponseCache`: iOS `APIClient.swift`, Android `data/ResponseCache.kt`; one file per full URL in the caches directory, pruned after 60 days). Only endpoints marked `keep: true` (iOS) or `@Headers("$KEEP: 1")` (Android) are saved. Loads go through `fetch`, which falls back to the saved answer only when the server is unreachable (no response, or a 5xx from the proxy), so a 404 still means gone. Each page's data has a `DataAge`; when a refresh fails it is marked `refreshFailed` and the "Couldn't refresh" banner under the header shows when the data was fetched, and tapping it calls `retryStale`. A new results endpoint needs the keep mark and a `fetch`, and a new page needs a case in `staleSince`.
- **AppModel loads overlap** whenever the user taps faster than the network. Every load re-checks `selectedEventID`/`selectedSessionID` after each await and bails if it lost; keep that when adding loads. Only events the user opens are persisted as `selectedEventID`; the launch default (newest GGLC event) is not.
- **Text sizes go through `egFont`, and table column widths through `egWidth`** (`Theme.swift`), so they follow the system text size; `.font(.system(size:))` does not. `RootView` clamps the range to `.large ... .xxxLarge`, and narrow leaderboard tables drop the HP column at the larger sizes. Navigation is hand-rolled: `RootView` owns the pinned back chip and the edge swipe, and both call `AppModel.goBack()`, so a new `Screen` needs a case there and in `backLabel`.
- **The app is called AutoX Live; "Evergreen" survives only in internal names.** The group's name is not ours to use, so nothing user-facing may carry it. The bundle ID, target/scheme/folder names, and `deploy.sh` artifact names keep it, and so must the Keychain service string in `DeviceIdentity.swift`: changing it orphans every installed device's token and with it their leaderboard ownership. App Store Connect copy lives in `Evergreen AutoX App iOS/AppStoreConnect.md`.
- The app's Support and Privacy links open `/support` and `/privacy` on the public server (`server/static/*.html`); the privacy page describes exactly what the app sends, so update it when that changes. The site root is the public landing page (`server/static/app.html`, also at `/app`, the URL given to TestFlight) with the TestFlight public link; its image strip in `server/static/landing/` is web-sized copies (900×1125 JPEG) of Ashlyn's marketing posts in `screenshots/marketing images - ashlyn/`, so re-export them when that set changes. `/updates` (`server/static/updates.html`) is the site's news page, newest post first. Its release notes come from the repo's GitHub releases through `GET /api/updates` (`server/releases.py`: grouped by version from the `ios-v2.0-3`-style tags, developer-only lines like merges, version bumps and screenshots dropped by `SKIP`, cached for `RELEASES_TTL` because unauthenticated GitHub allows 60 requests an hour), so edit a release on GitHub to change them. The iOS `deploy.sh` drafts each release's notes from the commits since the last tag (subjects as bullets, full messages as comments) and opens them in `$EDITOR` to be rewritten for users before creating the release (`-y` keeps the subjects); `./deploy.sh notes [ios-vX.Y-N]` rewrites an existing release's notes the same way. Other posts, like the Nutmeg outage, are written into the page with a `data-date` and the releases are slotted in around them; add a post there rather than a banner on the landing page. Tapping the version line in Setup seven times turns on dev mode, which shows the DEV section; its "Disable dev mode" button turns it off again.
- **Laps are keyed by finish position, not driver ID.** The Speedhive payload identifies drivers only by their position within a session; `/api/sessions/{id}/drivers/{position}` filters classification rows and laps on `position`.
- `speedhive-tools` is pinned to a commit in `requirements.txt`, and `app.py` reaches into its private internals (`speedhive.generated.api.session_controller`, `SpeedhiveClient._parse_response`) — verify those still work before bumping the pin.
- `server/static/index.html` is a single-file dev console (vanilla JS, tabs for Leaderboard/Acceleration/Speedhive/GGLC, plus the admin-only Submissions tab and an admin-only Moderation tab holding Reports, Bans and Users; the open tab is kept in the URL hash) and the test harness: when adding or changing API endpoints, keep it able to exercise them, and update the endpoint list in `API.md`. It is public at `/dev`, so it is read-only until an admin signs in: every control that writes (and the Reports and TrackAddict panels) carries the `admin-only` class, shown only while `body.admin` is set, which follows `GET /api/admin/session`. Signing in posts the credentials once to `POST /api/admin/session`, which answers with a 30-day HttpOnly `admin_session` cookie; the page never stores the password. The cookie is an expiry signed with a key derived from the admin credentials, so there is no session table, a password change signs every browser out, and sign-out only clears that browser's cookie. It is ignored on requests whose `Sec-Fetch-Site` is not `same-origin`, because `romangarms.com` counts as same-site. New write controls need the class too. This is presentation only; the server's auth is what actually protects writes. It hardcodes org ID `151294` as the test org. Number inputs must use `step="any"` — a mismatched `step` silently blocks form submission.
- Leaderboard write endpoints (POST/PATCH/DELETE under `/api/leaderboard`) take HTTP Basic admin auth (`LEADERBOARD_ADMIN_USER`/`LEADERBOARD_ADMIN_PASSWORD`; Basic auth returns 503 with no password set), the dev console's admin session cookie, or a device Bearer token the app mints on first launch (`DeviceIdentity.swift`, Keychain). Ownership is by token: `owner_id` on `courses`/`runs` **is** the token, so it must never appear in a response (`course_to_dict`/`run_to_dict` strip it and emit `is_owner` instead). Admin-created rows have no owner until an admin assigns one with `PUT /api/leaderboard/courses/{id}/owner` (the dev console's "Set owner"; the app's token is copyable from Setup in dev mode); `has_owner` is the only owner fact a response may carry. Anyone with a token can post runs to any course; only the poster, the course owner, or admin can change a run. `start.sh` writes the admin password to `.env` in single quotes, so it cannot contain `'`. Reads are public.
- **Accounts sit on top of device tokens.** `get_actor` upserts every Bearer token into `devices`, and once a device has signed in with Apple (`POST /api/account/apple`, verified in `server/apple.py`) it resolves `Actor.device_id` to the account's `apple:<sub>` string instead of the token. Every `owner_id`/`device_id` column therefore holds either a raw token or an account id, compared with plain equality, so new identity-keyed tables work across a user's phones for free; add them to `_adopt_device` (moves a device's rows to the account at sign-in) and `delete_account`. Neither form may appear in a response: use `devices.id`. Creating a board or posting a run needs an account (`_require_account`); editing does not. Revoking Apple's token on account deletion only happens when `APPLE_TEAM_ID`, `APPLE_KEY_ID` and `APPLE_PRIVATE_KEY` are set. Sign-in needs the nonce whose SHA-256 the app handed Apple (`AppleSignInButton` makes it, `apple.verify_identity_token` checks it). A revoked Apple ID is signed out two ways: `AppleCredentialWatcher` asks Apple on every activation, using the Apple user id kept in the Keychain by `DeviceIdentity.appleUser`, and Apple posts to `/api/account/apple/notifications`, which unlinks every device but keeps the posts. `AppModel.swift` must not import AuthenticationServices or touch `DeviceIdentity.appleUser`, or the macOS model harness stops compiling; credential handling stays in `AccountViews.swift`.
- **The admin names people by row id.** `GET /api/admin/users` (the dev console's Users panel) lists one entry per account with its devices nested, plus one per device that has not signed in; each carries `owned_course_ids` and `joined_course_ids`, which the panel's per-user Boards dropdown ticks; `_people` builds it and its `owner` field (the token or account id) must be dropped before anything leaves the server. Admin actions take `{kind: "user"|"device", id}` and `_person_owner_id` turns that into the stored identity: adding or removing a board member (`…/courses/{id}/members`), `POST /api/admin/bans`, and "Make owner". `POST /api/admin/devices/{id}/move` files a signed-out phone's posts under an account with `_adopt_device`. Labels exist on both `users` and `devices`. `IDENTITY_COLUMNS` lists every column that holds an identity; it drives the Users panel's backfill and `_prune_devices`, which drops device rows nothing refers to after 90 days or past 5000 of them, so a new identity-keyed table goes there as well as in `_adopt_device` and `delete_account`.
- **New-time notifications are pushed by the server** (`server/notify.py` watches, `server/push.py` talks to APNs). The watcher thread starts only when an APNs key is set (`APNS_*` in `.env`, `./start.sh push-key`) and polls every 15 seconds the events phones watch, plus today's GGLC and Speedhive AutoX events when anyone follows people by name, through the same `cache.cached` keys the app's requests use. The app sends its whole setup on every change with `PUT /api/push`: the APNs token, the two Setup toggles, the ME and pinned car numbers of each event from yesterday on, and the names it last marked (how it follows people into an event the phone has not opened). `push_registrations`/`push_watches` hang off `devices.id`, not an identity, because pins live per phone; a device with a registration is never pruned, and Apple's "gone" answer deletes the registration. An event's first poll only records what is there, so a restart or a new follower sends nothing old. The run filter mirrors the app's (`Driver.maxRunSeconds` and the 2x-fastest cutoff) and the GGLC ranking mirrors `gglcDrivers`, so change them together. Debug builds register as `sandbox`, TestFlight as `production`. The UIKit side (app delegate, permission, `PushNotificationWatcher`) lives in `PushNotifications.swift` so `AppModel` stays UIKit-free. The dev console's Users panel shows which phones have notifications on and can send one a test.
- Schema changes go in `db.ADDED_COLUMNS` (guarded `ALTER TABLE ADD COLUMN` on every connect). SQLite cannot add a column with a non-constant default, so new `created_at`-style columns are nullable and filled by the INSERT.
- Apple's user-generated-content rules are why the app has the guidelines gate (`GuidelinesGate`), report sheets (`POST /api/leaderboard/reports`, listed in the dev console's Reports panel), and a local "hide leaderboard" option. Keep those reachable when reworking the leaderboard UI. Moderation is the admin-only `hidden` flag on `courses`/`runs` (`PUT …/hidden`, the dev console's "hidden" checkboxes, also on each report): every read and write goes through `_get_course`/`_get_run`, which 404 hidden rows for non-admins, so new leaderboard queries must filter on it too. It is deliberately not in `CourseUpdate`/`RunUpdate`, or a poster could unhide their own content.
- **Blocks and bans are keyed by device token too**, so neither may echo one. A block (`/api/leaderboard/blocks`, device-only) makes the server drop the blocked poster's boards and runs from that device's lists and files a "Poster blocked" report; the app can only offer it where `has_owner` is true, so sheet-seeded rows cannot be blocked. A ban (`/api/leaderboard/bans`, admin-only, made from a report in the dev console) is checked in `require_actor`, so it stops every write, and it hides everything the device posted; lifting it does not unhide. The dev console has no device token, so it cannot exercise blocks.
- Text a device posts goes through `moderation.py` (`better-profanity` plus an allowlist, because its list flags "Dick", "Hooker", "strip", "stroke" and the like). Admin writes skip it.
- The custom leaderboard lives in `server/leaderboard.db` (SQLite, gitignored, auto-created by `server/db.py`). `server/import_sheet.py` seeds it from snapshots embedded in the script (the "HWY 9 Leaderboard" sheet, the WA Cannonball and Disco sheets, and the acceleration sheet) and backfills `region` on boards it already knows; it's idempotent. **Adjusted times are computed, not stored**: legacy runs (set on the old, longer course) are scaled by `distance_miles / legacy_distance_miles`. Average speed is likewise computed in `run_to_dict` (course distance ÷ raw time, legacy distance for legacy runs) whenever the distance is known, overriding any stored value. TrackAddict CSV logs carry lap times only in `# Lap N: HH:MM:SS.mmm` comment lines; `/api/trackaddict/parse` takes the raw CSV as the request body (no multipart) and lap 0 is the pre-start segment, not a run.
- **Boards are grouped by `courses.region`** (`CA`, `WA`, or null for app-created boards), which only an admin can set. The website's pages ask for `?region=`; the app lists every board. The WA page on the website finds its boards by name (`Cannonball North`, `Cannonball South`, `Disco Run`), so a rename has to happen in both repos.
- **Unlisted boards (`courses.unlisted`) fail closed.** `_listed_for` decides who an unlisted board exists for: its owner, a device with a `course_members` row (added by `POST /api/leaderboard/join` from the board's `join_code`), the admin, and the website's read key. Everyone else, requests with no credentials included, gets a 404 from `_get_course` and never sees it in the list, so new course queries must go through one of those two. The read key (`LEADERBOARD_READ_KEY`, sent as `X-Leaderboard-Key`; `./start.sh read-key` prints it, `new-read-key` replaces it) is what the website repo builds in as `VITE_LEADERBOARD_KEY`. It ships in a public bundle, so it is deliberately read-only and a separate credential: it never returns a join code and never satisfies `require_actor`. Join codes go only to the owner, members, and admin. When adding a credential or an access rule, keep that shape: no credentials means least access, and each capability gets its own secret.
- **The acceleration board is not a course.** It is one row per post in `acceleration_entries` behind `/api/acceleration`, ranked by 0-60 then 0-30 with missing times last; the list shows only a poster's best row per year and vehicle (compared case-insensitively) to everyone but the admin, with the rest nested in its `other_runs` (what the app's vehicle page lists), so deleting the best one brings the next back, and it follows the same rules as runs: public read, writes by a signed-in device or admin, `owner_id` stripped by `acceleration_to_dict`, edits only by the poster or admin, text through `moderation.py`, and `acceleration` as a `target_type` for reports, blocks and bans. `hidden` has no endpoint of its own; it rides on PATCH and is rejected there for anyone but the admin. The app opens the board from a fixed row at the top of the Leaderboards section and posts to it only from a TrackAddict drag-run log: `trackaddict.parse_log` adds `acceleration` to any lap that starts from a standstill, interpolating 0-30/0-60 from the GPS speed samples (1 Hz on a phone, so they are good to a few tenths) and reading the 1/8 and 1/4 mile from the `# Sector N: … (200m)`/`(400m)` markers that drag mode writes. Anything that walks a device's posts (`_adopt_device`, `delete_account`, `create_ban`, `list_devices`) has to include `acceleration_entries`.
- **A device's time comes from its log, never from the request.** `POST …/runs` and `POST /api/acceleration` require `log` (the raw TrackAddict CSV) and `lap` from anyone but the admin; `_logged_lap` parses it server-side, insists on the lap's time and GPS samples, and the time, top speed/trap speeds and `source` are taken from it (a `legacy` run's lap distance must match the legacy route). The poster cannot PATCH those fields afterwards (`RUN_LOGGED_FIELDS`, `ACCELERATION_LOGGED_FIELDS`); only the admin can. A forged CSV is still possible, but it has to be a whole plausible log. Tests build logs with `conftest.lap_log`/`drag_log_for`.
- **A hand-typed time is a submission, not a post.** The app's Post a Time sheets take either a TrackAddict log (posted at once) or a typed time with one photo (`POST /api/submissions`), which sits in `submissions` until the admin approves or rejects it in the dev console's Submissions tab; approving inserts the run or acceleration entry with the submitter as owner and `source` of `photo`. The photo is a file in `server/proofs/` (beside the database, gitignored, deliberately not in the database so it stays out of the backups), served only by the admin-only `…/proof` endpoint, and deleted the moment the submission is approved, rejected or deleted, which is what the privacy page promises. So submissions must be removed with `_delete_submissions`, never a bare DELETE or the cascade from their course (`delete_course`, `delete_account` and `_ban` all call it), and the image type is decided from the file's first bytes, not from anything the upload claims. `ProofPhotoBox` redraws the photo before upload to strip its location metadata; keep that if the picker code changes. `submissions.owner_id` is an identity column like the others.
- **Rate limiting is per caller address and in memory** (`ratelimit.py`, applied by the `rate_limit` middleware in `app.py`; limits in `LOGIN_LIMIT`/`SUBMISSION_LIMIT`/`WRITE_LIMIT`). Behind the proxy and Docker every peer is a private address, so the key is the *last* `X-Forwarded-For` entry, the one the reverse proxy appends; earlier entries are the caller's and are ignored, and a public peer is taken at its own address. If the proxy stops sending the header, every caller shares one allowance. Reads are deliberately unlimited because a whole event can share one venue or carrier address. Tests call `ratelimit.clear()` in the `client` fixture.
- **The Apple Watch app** (`Evergreen AutoX App Watch/`, its own target, embedded in the iOS app) shows the concept's two pages: ME's last run and the pinned friends. The phone sends it a `WatchContext` (server URL, event, session, ME car, pins, nicknames) through WatchConnectivity's application context (`WatchSync.swift`, driven by an `onChange` in `ContentView`), and the Watch fetches that session's results itself (`WatchModel.refresh`, every 10 seconds while on screen for an event from today or yesterday), so it stays live with the phone app in the background; it sends no device token. It compiles `APIClient.swift`, `Models.swift`, `SessionResults.swift`, `WatchContext.swift` and `AppIcon.icon` from the iOS folder through a membership exception in the pbxproj, so those must stay free of UIKit and of iOS-only code. `bump-version.sh` rewrites every target's version, which keeps the Watch app's version equal to the phone's, as App Store Connect requires.
- **CarPlay** (`CarPlay.swift`, driving-task entitlement) shows the Watch app's two pages as a tab bar: ME's last run and the pinned friends. It runs in the phone app's process but not through `AppModel`, since CarPlay can launch the app with no window scene and a locked phone stops the live refresh: `CarPlayFeed` takes the same `WatchContext` from `ContentView`, saves it for that cold launch, and polls the session itself every 10 seconds while connected. Driving-task apps are limited to list, information, grid and tab bar templates. The scene is declared in `Info.plist`, so `UIApplicationSceneManifest_Generation` must stay off or the generated manifest wipes it. The follow rules (ME, friends, gaps, nicknames) live on `WatchContext` so the Watch and CarPlay share them.
- `format_time` drops the fraction from whole-second times of an hour or more (`1:00:50`), because the app's time column is sized for `m:ss.mmm`.
- **Android releases are files, not database rows.** `GET /api/android/release` reads `release.json` (`version_name`, `version_code`, `sha256`, `size`, `file_name`) from `server/android/` (beside the database like `proofs/`, gitignored) and 404s unless the APK it names is there; `GET /android` serves that APK as `AutoX-Live-<version>.apk`. The Android `deploy.sh` uploads the APK first and `release.json` last, so the app never sees a version whose file is missing. On the public host the directory has to be mounted in the untracked `docker-compose.override.yml` (`- ./server/android:/app/server/android`) or releases vanish on rebuild. The privacy page says the update check sends no device ID.
- Backups: `server/backup_db.py` snapshots the DB into `/mnt/Data/Backups/autox-leaderboard/` (hourly via the user crontab on the public server, deduped by content, newest 365 kept). `restore FILE` swaps a snapshot in and leaves the old DB as `leaderboard.pre-restore-*.db`; the server must be restarted afterwards.
- **Android mirrors the iOS app's logic by hand.** `data/Models.kt` and `AppViewModel.kt` port `Models.swift`, `SessionResults.swift` and `AppModel.swift`; the run filter (`Driver.MAX_RUN_SECONDS`, the 2x-fastest cutoff) and the GGLC ranking now exist in three places, and `tests/data/run_filter_cases.json` is read by both `tests/test_run_filter_parity.py` and the Android `RunFilterParityTest`, so change all three together and extend the fixture. Driver and compare routes are keyed by car number, not position, so a refresh keeps them on their driver. Android tests: `./gradlew :app:testDebugUnitTest` in the Android folder. Debug builds (`.debug` suffix) hit `http://10.0.2.2:8321` (the emulator's host) unless built with `-PautoxDevBaseUrl=...`; cleartext is allowed only for the hosts in `app/src/debug/res/xml/network_security_config.xml`. The release keystore and `release.properties` are gitignored; losing the keystore means no install can ever be updated. `versionCode` is `major*10000 + minor*100 + build`, and `bump-version.sh` sets the Android version with the iOS one.
- **Race Monitor live timing is a TestFlight-only stopgap.** Evergreen Speedway sends its live timing only to Race Monitor (Speedhive gets the results after the event). The server reads the feed Race Monitor's public web widget uses, which its terms reserve for authorized apps; the owner accepted that for TestFlight, and the feature must be dropped or moved to an authorized feed (an API key, or the speedway relaying Orbits' RMonitor output) before any App Store submission. `server/racemonitor.py` scans Race Monitor's live page every 10 minutes for races matching `RACEMONITOR_MATCH` (default `evergreen`, which hits the track name "Evergreen Speedway") plus races an admin added in the dev console, and while a race is within two hours of its schedule it holds one websocket and saves every session into `racemonitor_events`/`racemonitor_sessions` every 5 seconds. The feed carries no lap history, only what crosses after joining (plus each car's best and last lap), so the server records rather than connecting on demand; a session seen before resumes from its saved state. Recorded events and sessions take IDs from `racemonitor.ID_OFFSET` (2,000,000,000) up and answer through the Speedhive endpoints, so the apps, Watch, CarPlay and `notify.py` treat them as Speedhive events with no client code; keep that range clear of Speedhive's and inside a 32-bit int (Android's IDs are `Int`). `GET /api/orgs/{SPEEDHIVE_ORG_ID}/events` adds a recorded event only while Speedhive has no event on its date, so the official upload replaces it. `RACEMONITOR=off` stops the threads. `server/rmonitor.py` parses RMonitor lines into Speedhive-shaped rows; a crossing's `$J` and the `$G` that counts it come in either order, paired by total time, and `$RMHL` gives exact lap numbers. Competitors are keyed by registration number, not car number. `server/racemonitor_watch.py RACE_ID [--record FILE]` / `--replay FILE` is the hand tool for looking at a feed.
